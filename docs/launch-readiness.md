# Подготовка APPGRADE к запуску

Домен куплен в REG.RU. Конкретное имя домена и вариант размещения пока не подтверждены. Рабочие DNS, секреты и инфраструктура этой подготовкой не изменены.

## Что уже подготовлено

- Страницы политики и отдельного согласия, обязательное согласие в формах и запись его версии/времени.
- Блокировка приёма персональных данных при незаполненных реквизитах оператора.
- Проверка готовности базы и реквизитов оператора через /api/health.
- Production-шаблон: deployment/production.env.example. Секреты заполняются только в настройках хостинга или приватном файле .env.
- Docker передаёт веб-приложению реквизиты оператора; публичные контакты Сибая передаются и на сборку, и при запуске.
- Опциональный HTTPS-прокси Caddy: compose.production.yaml и deployment/Caddyfile.
- Резервная копия Docker PostgreSQL: scripts/backup-db.sh. Сохранённые файлы не удаляются автоматически.

## Что нужно заполнить

1. Имя купленного домена. APP_ORIGIN и NEXT_PUBLIC_SITE_URL должны совпадать: https://ваш-домен. SITE_DOMAIN для Caddy содержит только имя домена без https://.
2. Адрес оператора SELLER_ADDRESS. Остальные реквизиты взяты из предоставленного документа ИП.
3. Адрес, телефон и график магазина в Сибае.
4. Поставщик и страна размещения базы; фактическая схема обработки данных через хостинг. Проверить требования к локализации, уведомлениям и договорённостям с обработчиками до сбора данных.
5. Пароль админки не короче 20 символов. Для Compose использовать случайный буквенно-цифровой пароль PostgreSQL не короче 20 символов.
6. Подтвердить условия гарантии 5 лет, рассрочки 0/0/36, кешбэка, акции с Алисой, доставки и Trade-in, уже размещённые на сайте.

## Вариант A: Vercel с собственным доменом

- Добавить купленный домен в проект Vercel; в REG.RU установить именно записи, которые покажет Vercel для этого проекта. Не использовать произвольные IP или старые значения из примеров.
- В Production Environment Variables заполнить настройки из deployment/production.env.example, кроме POSTGRES_PASSWORD, BACKUP_DIR и SITE_DOMAIN (они для собственного Docker-сервера). TRUST_PROXY оставлять false без подтверждённого доверенного прокси.
- Подключить выбранную базу, выполнить npm run db:migrate на доверенной машине с приватным DATABASE_URL.
- Заявки сохраняются в PostgreSQL и просматриваются в /admin. Отдельные боты не нужны.
- После задания NEXT_PUBLIC_* выполнить новый deployment: клиентские значения встраиваются во время сборки.
- Настроить резервное копирование у поставщика базы и проверить восстановление в отдельную тестовую базу.

## Вариант B: отдельный сервер с Docker

Скопировать шаблон в приватный .env, заполнить значения; существующий рабочий .env не перезаписывать. Сервер должен принимать соединения на 80/443. В REG.RU направить домен на подтверждённый адрес сервера; AAAA добавлять только при рабочем IPv6.

```sh
docker compose -f compose.yaml -f compose.production.yaml config --quiet
docker compose -f compose.yaml -f compose.production.yaml up -d --build
docker compose -f compose.yaml -f compose.production.yaml ps
```

Caddy получает и обновляет сертификат для SITE_DOMAIN. Прокси перезаписывает X-Real-IP; web доступен с хоста только через loopback-порт. Сертификаты сохраняются в отдельном volume. Не выполнять docker compose down -v на рабочем сервере.

## Проверки перед открытием заявок

```powershell
npm.cmd run lint
npm.cmd test
npm.cmd run build
npm.cmd run check:launch -- --env-file=.env.production --url=https://ваш-домен
```

Файл .env.production используется в примере как приватный файл подтверждённых production-настроек. Явный --env-file исключает автоматическую загрузку .env.local/.env; уже заданные переменные процесса имеют приоритет. Проверка не выводит значения секретов.

- /api/health должен вернуть HTTP 200 и ordersAvailable: true. После этого отдельно проверить сохранение заявки и её отображение в админке.
- Проверить карточки, город, корзину, политику, согласие, мобильный экран и переключение баннеров в браузере.
- С согласованными тестовыми контактами отправить один заказ и одну заявку Trade-in; сверить ID, сумму, город и появление обеих заявок в /admin. Рабочие заявки при подготовке не создавались.
- Проверить повторную отправку: одна заявка, без дубля; подмена цены и отсутствие согласия должны отклоняться.

## Резервные копии Docker PostgreSQL

```sh
sh scripts/backup-db.sh
```

Скрипт сохраняет custom-format pg_dump в BACKUP_DIR (по умолчанию ./var/backups), с закрытыми правами доступа и уникальным именем. При ошибке оставляет .partial и возвращает ненулевой код; успешная копия не подменяется неполной. Скрипт не меняет данные и не восстанавливает рабочую базу.

Запускать по расписанию, например ежедневно, и контролировать код завершения. Копировать зашифрованную копию вне основного сервера. Проверку восстановления выполнять в отдельной новой базе. Сроки хранения резервных копий согласовать с политикой обработки данных.

## Состояние подготовки

Локальные проверки: lint прошёл, 65 тестов прошли, production-сборка Next.js завершилась успешно. Проверка production-шаблона ожидаемо отклоняет запуск с пустыми реквизитами, паролями и доменом-заглушкой.

Рабочие DNS, HTTPS-сертификат, Docker Engine, выбранный сервер и сохранение заявок на нём требуют проверки после выбора размещения. Docker и резервное восстановление локально не запускались: Docker Engine в этой среде отсутствует. Публикация и включение продаж не выполнены. Политика остаётся проектом до заполнения адреса и подтверждения фактической схемы обработки данных.
